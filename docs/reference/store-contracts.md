# Repository transaction contracts

`cigar-store` exposes capability-bound transactions instead of an unscoped key/value interface.

- `AccessContext` fixes tenant and purpose when a transaction opens. Repository methods accept no later tenant override, preventing a handle from crossing tenant scope.
- `SnapshotSelection` chooses latest-at-open or an exact retained `StoreRevision`. An `AtomCursor` embeds that revision and fails with `MixedSnapshot` in another snapshot.
- `begin_write` binds an exact expected revision. Commit validates all staged protocol records, referential integrity, context/effect sequence and parent links, blob digest/size, derivation acyclicity, and outbox causality before one atomic state publication.
- `IdempotencyIdentity` binds operation scope and secret-safe caller key to the normalized request digest. Repeating that identity returns the original receipt even with a stale expected revision; reusing its key for different semantics fails closed.
- `CancellationToken` is checked before work and again at the publication boundary. Dropped, cancelled, stale, invalid, and failpoint-aborted writes expose no partial state.

The in-memory backend retains immutable whole-state revisions to make the oracle easy to reason about. Production backends can use database MVCC, but observable behavior must match the reusable conformance suite exactly.

Migration plans are append-only, checksum-addressed, application-version bounded, classified online/offline, and require explicit lock behavior, verification, and rollback-or-restore instructions. The repository authority is `migrations/authority-v1.json`; its closed validator rejects rewritten history, gaps, unlisted SQL, mirror drift, unsafe paths, and transaction control inside migration sources. Mixed-version participants must embed the same exact catalog and every installed row must span the running application major. Database-owned metadata never authenticates an unknown future suffix, even if it self-declares itself online. Startup treats unknown, offline, or version-incompatible state as an unsupported downgrade and fails without mutation. The historical sequence-one exact-count reader is not a rolling participant and refuses sequences two through four.

## Durable local profile

`SqliteStore` verifies the bundled SQLite version and FTS5 capability at startup, then enables WAL, `synchronous=FULL`, foreign keys, defensive mode, secure delete, a 32 MiB page cache, a 30-second busy timeout, and bounded WAL checkpoints. The connection mutex is the single writer serializer. Each read transaction owns an independent read-only connection, begins `DEFERRED`, and pins its revision on the first residual metadata read. Catalog methods then use tenant/revision indexes against that same SQLite snapshot; callers should release long-lived readers promptly because a live SQLite snapshot can retain WAL frames.

Sequence four atomically converts each retained legacy state into a catalog-free residual revision and normalized authoritative atom/edge rows, then deletes legacy whole-state bytes and activates one format/profile singleton in the same immediate transaction. A crash before commit leaves legacy authority intact and restart repeats the backfill; a crash after commit observes a complete active v4 database. Migrated semantic roots preserve the legacy checksum; new revisions bind revision, residual checksum, bucketed catalog root, counts, and referenced bytes. Every revision also has an external fsynced revision anchor. A database behind its anchor is rejected; a database ahead advances the anchor during recovery.

The retained SQLite sequence-one fixture upgrades through sequence four without changing its canonical semantic-state root. Migration-ledger failure tests cover bootstrap plus transaction begin, schema SQL, both sides of ledger insertion, and both sides of commit for each appended sequence; activation tests additionally require complete v4 authority or intact legacy state. Restart converges to all four immutable ledger rows and an empty legacy snapshot table. The macOS PostgreSQL gate remains independent and uses fresh private-CA TLS and separate migrator/runtime roles.

Production blob writes compose the database with `RepositoryBlobStore`. Encrypted bytes are fully written, flushed, fsynced, renamed, and parent-directory-synced before SQLite metadata commits. Failures before metadata commit leave no visible reference; startup reconciliation quarantines the orphan. Authentication failures and swaps create durable, bounded digest-only invalidation markers for downstream processing. SQLite state contains blob references only and never blob plaintext.

Authoritative atoms and edges are immutable normalized rows with publication revisions, per-record checksums, indexed lineage validity intervals, and deterministic 16-bit integrity buckets. A catalog commit inserts only new rows, recomputes touched bucket roots, and streams the fixed-size bucket table into the revision catalog root. The default profile remains capped at 4 GiB. `local_sqlite_capacity_profile = "large_local"` is an explicit macOS-arm64-only database binding with a 64 GiB cap, a 300 GiB initial free-space requirement, a 16 GiB runtime reserve, and hard logical limits of 1.25 million atoms, 12.5 million edges, and 128 GiB referenced blob bytes.

Atom and FTS5 projections remain disposable immutable generations. Rebuild and verification stream authoritative v4 atom rows in tenant/version order rather than materializing the graph. A generation records the exact authoritative revision and semantic root, bounded atom count, and ordered-row root; activation repeats that binding. Every projection read fails closed after a newer commit. Startup rebuilds corrupt, incomplete, missing, or stale projection state and retains at most two complete generations.

## Keys, backup, restore, and GC

`EncryptedDevelopmentKeystore` encrypts the complete private provider state with an Argon2id-derived key. `OsKeychainKeyProvider` obtains that file key from the native operating-system credential store. Rotation prevents new encryption with retired keys while retaining historical decryptability until destruction.

`create_backup_with_effect_checkpoint` uses SQLite's online backup API and copies encrypted blob files into a temporary archive while an immediate transaction excludes metadata writers. Before that lock is released, the production checkpoint capture takes the external cross-process checkpoint lock, proves that every latest effect envelope has exactly one matching `(tenant, effect, intent, version, authenticator)` entry and that no extra entry exists, and durably creates `effect-checkpoints.json`. Disposable projection generations are removed and the database copy is vacuumed before inventory, so projection timestamps or generation numbers cannot change the canonical backup root. The format-two signed CBOR manifest contains the database and checkpoint, schema/repository versions, every file size and checksum, required opaque key references, and a deterministic root. `verify_backup` validates signature, inventory, checksums, root, schema, revision, SQLite structure, and state checksums; the production CLI additionally requires format two and revalidates exact database/checkpoint semantics.

`restore_backup` accepts only a nonexistent or exactly empty target, verifies before copying, checks the restored database before activation, and atomically renames the result. Production restore also requires the archived checkpoint to equal the current external monotonic checkpoint exactly and holds its operating-system lock through copy, verification, and publication. A newer current checkpoint, an older current checkpoint, an unsigned format-one archive, or any database/checkpoint substitution fails closed; restore never rewrites or repairs external checkpoint truth. The restored directory is a recovery target, not an automatic live-state activation, and must be activated only while effect writers are stopped.

Physical blob GC requires satisfied retention, no legal hold, and completed backup policy. `SqliteStore::plan_garbage_collection_blob_roots` derives the complete tenant mark set from its latest checksum-verified state while holding the writer lock, then the operator signs the exact revision, ordered candidates/root, bound, and policy. `run_garbage_collection_plan` accepts only opaque cryptographically verified evidence, reacquires the writer lock, requires the exact current revision, and requires the complete bounded candidate set to match before a first deletion. While that lock remains held it durably publishes an owner-private execution marker bound to the canonical database path identity and every signed plan field, then passes only the signed set to the physical store. A retry may tolerate already-absent signed candidates only when that exact marker proves the run previously crossed its deletion boundary; newly visible orphans remain outside the deletion call. Without the marker, same-revision addition, removal, or substitution fails before deletion. A concurrent blob-before-metadata publication therefore cannot be collected, and callers cannot supply live roots or bypass the signed plan through the legacy preview API.
