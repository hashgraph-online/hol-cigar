# CIGAR 0.14.2 performance iterations

## Baseline — retained 0.14.1

Created the branch from current remote main/release 0.14.1 without changing other
worktrees. Recorded ten real cold SDK calls and preserved a source-built baseline
worker with the existing release/features profile. Worker initialization dominates
the roughly 161 ms cold native query. Existing authored quality scores are 100/100.

## Iteration 1 — exact count-only tokenizer construction

The ordinary-counting API used a general CoreBPE that also constructs decoder,
special-token, sorted-encoding and 128 regex-thread structures. The candidate
loads the identical pinned vocabulary into one read-only encoder and uses the
same upstream regex and merge rules. Short pieces use the pinned public merge;
long pieces retain the upstream heap/rank/start behavior, counting surviving
tokens without building an unused decode result. Cache boundaries and limits,
tokenizer identity, graph selection and security controls are unchanged.

Added vocabulary-hash, reference-parity, long-input and concurrent-count tests.
The first test build exposed a SHA-256 test-format incompatibility with the pinned
sha2 release; the assertion now compares exact digest bytes. This was a test
compilation issue, not an observed engine result. Measurements and gate results
will be appended after executing the candidate.

The three new release-mode tests passed: pinned vocabulary identity, reference
parity for 2,028 Unicode/special/long/varied inputs, and eight-thread counting.
Ten real prototype calls measured median initialization 31.12 ms and cold
initialization/ingest/compile 33.56 ms, versus 154.14/161.29 ms in the retained
release baseline. Repeated compile median was 0.36 ms versus 0.79 ms. This is a
prototype profile, not yet the paired benchmark acceptance gate. The prototype
still negotiated 0.14.1; its exact binary and all raw observations are preserved.

## Iteration 2 — version integration and full verification

Kept the faster exact counter, advanced native/Python/TypeScript metadata together
to 0.14.2, and retained the protocol, ABI and security floors. Added the vocabulary
and MIT notice suffix to release source capture so the new build inputs are bound.
Release tag gates target the new version without weakening their checks. Next:
paired benchmark, old-snapshot compatibility, full native/SDK boundary tests and
immutable patch security review.

The official packaged native build passed, including all context, broker,
persistence and snapshot tests. The first SDK test pass retained its failures:
Python lacked installed distribution metadata, Node's nested script lacked the
private pnpm directory on PATH, and the Node release assertion still expected
0.14.1. Installed the explicitly permitted portable development SDK with a
matching trusted worker, corrected PATH, and updated the exact release assertion,
lockfile identity, stalled-worker fixture and signing-handoff allowlist to 0.14.2.
No test assertion or security gate was removed. The first release test pass also
used macOS LibreSSL without Ed25519 support; rerun with the existing OpenSSL 3
installation rather than skipping signing tests. Original JUnit results remain.

Extended reference parity to 2,040 cases with mixed long alphabetic/punctuation
pieces around the heap threshold and up to 32,768 bytes, and added a regression
that changing the embedded vocabulary invalidates the release source binding.
Added an executable compatibility check using the unchanged release corpus,
complete outputs and bidirectional snapshot/delta verification. Final paired
measurement and SDK results are pending.

## Iteration 3 — checked merge invariants

The strict Clippy gate rejected unchecked indexing in the upstream-derived heap
loop (the repository already denies `indexing_slicing`). Replaced direct indexing
with checked access, used byte windows for initial pairs, checked the surviving
token decrement, and made an inconsistent neighbor invariant return `Tokenizer`
instead of relying on a debug assertion. No lint allowance was introduced.
Clippy now passes with `-D warnings` across all context targets/features.

The clean packaged iteration-2 worker passed native tests. Its Python SDK passed
523 tests plus 39 subtests with zero skips once both real and stalled workers were
supplied. Release integrity checks passed 74 tests plus 96 subtests using OpenSSL
3; core-only tests also passed. The final measurement will use the newly packaged
iteration-3 worker after rechecking the expanded parity corpus and SDK boundaries.

## Final verification and acceptance

The clean iteration-3 packaged worker passed 148 native tests and the final SDK
passes: Python 523 tests plus 39 subtests, Node 163 individual cases, zero SDK
skips. All 2,040 tokenizer oracle cases agree. The unchanged release corpus
matches in all 172 cases (155 successes/17 expected errors); 155 snapshot/delta
pairs verify bidirectionally. Both immutable implementation security reviews
completed with zero confirmed findings and their actual local scope recorded.

Executed the complete 540-cell declared paired matrix once, preserving every
original attempt. Both reports scored and replayed. All 270 complete paired
response envelopes and graded semantic observations agree. At budget 2048 the
median of 18 task medians fell 186.7438 → 83.5866 ms (**55.24%**) and their mean
fell 180.0195 → 76.3252 ms (**57.60%**). Evidence/graph scores remain 100/100.
The target passes; no additional engine changes were made to chase these scores.

The separate dashboard comparison session uses the same two version-bound
artifacts. The project Change log shows these real engine iterations, explicitly
attributed to the current coding task rather than the automatic repair driver.
See [the results and reproduction instructions](0.14.2-results.md) for startup,
whole-cell timing, raw evidence identities and verification limits.
